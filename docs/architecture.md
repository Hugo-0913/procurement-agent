# 技术方案

**版本：** v1.0
**日期：** 2026-09-17
**配套文档：** `PRD.md`（需求）、`plan.md`（实施计划）、`docs/decision-log.md`（决策与验证记录）

---

## 1. 目标与约束

本方案要解决的核心技术问题是：**如何让一个由 LLM 驱动的多 Agent 系统，在长周期、多异常、需人工介入的业务流程中保持可控、可观测、可恢复、可复现**。

约束条件（决定了方案形态）：

| 约束 | 影响 |
| --- | --- |
| 本地 Windows，无 Docker、WSL 不可用 | 沙箱只能做进程级隔离，不能做容器隔离 |
| 仅 DeepSeek 单一模型 | 工具调用稳定性低于顶级模型，需靠工程手段补偿 |
| 模型调用成本需可承受 | 必须有评测能力，靠固定用例集反复跑 |
| 必须是可演示的求职作品 | 可观测性与可解释性优先于功能数量 |

---

## 2. 总体架构

系统分为五层，依赖方向自上而下单向流动：

```
┌─────────────────────────────────────────────────────────────┐
│ 接入层   FastAPI + 原生 JS + SSE                              │
│          任务看板 / 采购执行页 / 数据台 / 评测页                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST + SSE
┌───────────────────────────▼─────────────────────────────────┐
│ 编排层   LangGraph StateGraph + SqliteSaver                  │
│          阶段流转 / 审批中断 / 断点恢复 / 唯一状态源             │
└───────────────────────────┬─────────────────────────────────┘
                            │ 阶段处理器
┌───────────────────────────▼─────────────────────────────────┐
│ 智能体层  DeepAgents                                         │
│          主 Agent（协调） → 资质核验 / 比价分析 / 订单执行       │
└───────────────────────────┬─────────────────────────────────┘
                            │ 工具调用
┌───────────────────────────▼─────────────────────────────────┐
│ 治理层   策略守卫 / 上下文摘要 / 反思重试（中间件）              │
└───────────────────────────┬─────────────────────────────────┘
                            │ 受控访问
┌───────────────────────────▼─────────────────────────────────┐
│ 能力层   虚拟文件系统 / 持久化记忆 / 技能注册表 / mock ERP / 沙箱 │
└───────────────────────────┬─────────────────────────────────┘
                            │
                    ┌───────▼────────┐
                    │ SQLite（唯一）  │
                    └────────────────┘
```

**为什么状态机在 Agent 之上，而不是之内：** 任务状态需要跨进程生命周期存在、需要在人工审批处挂起数小时至数天、需要被 Web 层实时查询与渲染。这些需求超出了 Agent 运行时内存态的规划能力，因此状态机必须是外置且唯一的状态源。

## 3. 技术选型与理由

| 层面 | 选型 | 理由 | 备选方案与代价 |
| --- | --- | --- | --- |
| 流程编排 | LangGraph `StateGraph` + `SqliteSaver` | 原生支持中断与恢复，checkpoint 落库，与 deepagents 同源（deepagents 基于 LangGraph 构建） | 自研轮询式状态机：可控性更高，但要自己实现 checkpointer，与 Agent 运行时割裂 |
| Agent 运行时 | deepagents | 项目定位要求；自带子 Agent 委派与文件系统抽象 | 纯 LangGraph 自研：代码量更大，但可完全掌控委派流程（保留为降级方案） |
| 模型 | DeepSeek（OpenAI 兼容接口） | 成本足够低，可支撑 30 条用例反复评测 | 顶级模型：工具调用更稳但成本高，不适合做评测基线 |
| 持久化 | SQLite | 单机演示无运维成本，checkpoint 与业务数据可共用一个文件 | PostgreSQL：对演示场景属过度设计 |
| Web | FastAPI + 原生 HTML/JS + SSE | 本机 Node v14 无法支撑现代构建链；SSE 实现简单且单向推送足够 | React + Vite：开发体验更好但引入构建依赖与环境风险 |
| 沙箱 | 进程级双层隔离 | 本机无 Docker，容器方案无法落地 | 容器 / 微 VM：隔离强度更高，作为生产化演进方向写在 `docs/sandbox-security.md` |
| 测试 | pytest + 可注入模型替身 | 测试必须离线可跑，且评测结果需可复现 | 真实模型测试：结果不稳定、成本不可控，仅用于冒烟验证 |

## 4. 关键设计决策

### ADR-001 状态机归属：外层自研为唯一状态源

**背景：** deepagents 内置 planning（todo 列表）机制，天然也能"记状态"。

**决策：** 任务状态由外层 LangGraph 状态机管理，落 SQLite；子 Agent 内部的 todo 仅作为局部推理草稿，不参与状态管理，也不被 Web 层读取。

**理由：** 单一状态源可以避免两套状态不一致；审批中断要求状态在进程外持久化；页面渲染需要稳定可查询的状态模型。

**代价：** 状态流转需要显式编码，不能依赖框架自动规划；新增阶段时必须同时更新转移表、handler 与页面阶段条。

### ADR-002 子 Agent 职责切分：确定性优先，LLM 兜底

**背景：** DeepSeek 的工具调用稳定性弱于顶级模型，若让模型自由决定"查哪些供应商、怎么比价"，失败率会显著上升。

**决策：** 三个子 Agent 的核心判定（资质筛选、成本计算、阈值判断）实现为**确定性纯函数**；LLM 只负责需求解析与自然语言说明生成。委派由状态机阶段驱动，而非由模型自由路由。

**理由：** 把不可靠的部分压缩到最小；纯函数可单测、可复现，评测结果才有意义。

**代价：** 业务规则变化需要改代码而非改提示词；"智能感"降低，但可解释性大幅提升——这在面试场景中是加分项而非减分项。

### ADR-003 技能系统：渐进式加载

**决策：** 四个技能以 `SKILL.md` 存放，主 Agent 初始只加载 frontmatter 中的名称与描述；正文仅在对应阶段被显式加载。

**理由：** 直接内联四个技能的正文会长期占用大量上下文；渐进式加载让"能力扩展"与"上下文成本"解耦，且加载行为可观测。

**代价：** 需要显式的加载时机设计；若加载时机判断错误，Agent 会在缺少领域知识的情况下作答（通过阶段与技能的固定映射规避）。

### ADR-004 上下文治理：结构化保留 + 工具结果折叠

**决策：** 摘要中间件触发时，保留采购要素、各阶段结论、未决问题与审批状态（结构化字段），折叠完整的工具返回原文为一行摘要。

**理由：** 长任务的上下文膨胀主要来自工具返回原文，而非关键结论。按类别折叠比整体摘要更安全，因为关键字段永不被摘要模型改写。

**代价：** 需要维护"关键字段"清单；字段增多时中间件复杂度上升。

### ADR-005 双层安全沙箱（进程级）

**决策：** 第一层策略校验（路径白名单、命令黑名单、金额阈值、审批判定），第二层执行隔离（受限子进程、环境变量白名单、超时、输出上限、网络关闭）。

**理由：** 两层职责不同——第一层决定"能不能做"，第二层保证"就算放行也做不出格"。二者可独立测试。

**代价：** 进程级隔离无法防御内核级逃逸，安全强度低于容器方案。因此该限制必须显式写入安全文档，作为生产化演进项，而非隐去不谈。

### ADR-006 错误处理：分类驱动的反思重试

**决策：** 异常分为可重试（超时、连接失败、结构化输出校验失败）与不可重试（策略拒绝、业务性失败、参数缺失）两类；重试次数上限可配置，每次重试记录原因与修正动作。

**理由：** 无差别重试会把业务性错误变成死循环；分类后重试才有意义，且重试原因本身成为可观测数据。

**代价：** 分类表需要随新增异常类型维护。

## 5. 模块划分与依赖方向

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| `web/` | HTTP 接口、SSE 推送、页面渲染 | 编排层、能力层（只读） |
| `state/` | 状态定义、合法转移表、事件存储、图编排 | `db/`、`config.py` |
| `agents/` | 主 Agent 与三个子 Agent、模型工厂、配置加载 | 能力层、治理层 |
| `middleware/` | 策略守卫、上下文摘要、反思重试 | `state/`、能力层 |
| `sandbox/` | 策略引擎、受限执行器 | `vfs.py`、`config.py` |
| `erp/` | mock ERP 仓储与故障注入 | `db/` |
| `memory/` | 采购偏好与供应商历史沉淀 | `db/` |
| `skills_loader.py` | 技能发现与渐进式加载 | 文件系统 |
| `vfs.py` | 虚拟文件系统与路径逃逸防护 | 无 |

**依赖规则：** 能力层不得反向依赖编排层与 Web 层；`vfs.py` 与 `sandbox/executor.py` 不依赖任何 Agent 代码，保证可独立测试。

## 6. 数据与事件模型

**两张核心表：** `tasks` 保存当前状态与结构化输入；`task_events` 保存不可变的追加式事件流。

**为什么用事件流：** 页面的任务树与时间线本质是同一份事件流的两种视图——任务树按 `agent` 与 `tool_call` 聚合，时间线按 `seq` 平铺。用事件流而非多张状态表，可以让"过程可视化"零额外成本，同时天然支持 SSE 增量推送（客户端只传 `after_seq`）。

**事件类型：** `stage_change`、`agent_delegation`、`tool_call`、`tool_result`、`skill_loaded`、`policy_denied`、`retry`、`context_summarized`、`approval_requested`、`approval_decided`、`memory_loaded`、`memory_written`、`error`、`task_finished`。

**恢复能力：** 业务状态在 `tasks`，编排状态在 LangGraph checkpoint 表，两者写在同一 SQLite 文件中，保证进程重启后两者一致。

## 7. 关键时序

**正常路径：** 提交需求 → 创建任务（`PENDING`）→ 解析（`PARSING`，加载需求解析技能与采购偏好记忆）→ 委派资质核验（`QUALIFYING`）→ 委派比价分析（`SOURCING`，加载比价技能）→ 生成订单草稿（`ORDER_DRAFTING`）→ 策略引擎判定无需审批 → 写入订单（`ORDERED`）→ 完成（`COMPLETED`）→ 回写记忆。

**审批驳回路径：** 草稿金额超阈值 → 策略引擎命中规则 → 写入 `AWAITING_APPROVAL` 并 `interrupt` → 页面弹出审批卡片 → 审批人填理由后驳回 → 恢复执行 → 转入 `REVISION_REQUIRED` 再回 `SOURCING` 重新选型 → 第二轮比价结论与第一轮并存于事件流，页面可对比。

**中断语义：** `AWAITING_APPROVAL` 是持久化挂起而非进程阻塞，进程重启后任务仍可被审批并续跑。

## 8. 与 DeepAgents 的集成契约

以下四点必须在 Task 2 的冒烟验证中确认，结论写入 `docs/decision-log.md`：

1. **子 Agent 委派方式**：是通过 `create_deep_agent` 的 `subagents` 参数注册，还是需要手写工具封装。
2. **中间件挂载点**：策略守卫、摘要、重试三个中间件的 hook 名称与触发时机。
3. **虚拟文件系统接口**：框架自带文件系统抽象与我方 `vfs.py` 的边界如何划分（谁来承担路径校验）。
4. **状态隔离方式**：子 Agent 是否能共享或必须隔离会话状态，以及其与 LangGraph checkpoint 的关系。

**降级方案（若委派验证失败）：** 保留 deepagents 作为 Agent 构造与工具调用层，但在 LangGraph 节点内直接调用子 Agent 接口，不使用框架的自动委派路由。届时决策记录中必须写明降级原因，且 PRD 的"委派架构"表述需相应调整。

## 9. 风险与缓解

| 风险 | 触发条件 | 缓解措施 |
| --- | --- | --- |
| DeepSeek 工具调用不稳定 | 冒烟测试失败或评测成功率低 | 职责切窄、限制单轮工具调用数、结构化输出校验、ADR-006 的受限重试 |
| 框架 API 与文档不符 | 冒烟测试中签名不匹配 | 锁定版本号并记录实际签名，代码以实际签名为准 |
| 审批中断恢复失败 | 重启后无法 resume | checkpoint 与业务表同库事务写入；Task 6 有专门的跨进程恢复测试 |
| 摘要丢失关键信息 | 压缩后字段缺失 | 关键字段结构化保留，不进入摘要模型；压缩后校验字段完整性 |
| 评测结果不可复现 | 引入随机性或真实模型 | 固定种子、固定用例集、离线模型替身；Task 24 有可复现性测试 |
| 范围蔓延 | 开发中不断加需求 | 新需求记入 v2 待办，不插入 v1 |
