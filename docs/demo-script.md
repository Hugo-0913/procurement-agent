# 5 分钟演示脚本

目标：让观看者在 5 分钟内理解系统做了什么、架构如何运作、异常如何处理、指标从哪来。全程停留在页面内，不切换终端。

## 00:00–00:40 提交需求

动作：打开任务看板页，点「填入示例需求」，展示文本框内容 `采购 50 箱 A4 纸，下周一前到货，成本中心 CC-1001`，点提交，页面跳到采购执行页。

讲解要点：需求是自然语言，系统需要先把它解析成结构化采购要素，而不是直接去查价格。

## 00:40–02:00 观察委派与技能加载

动作：指着左侧技能区——四个技能初始都是虚线「仅描述」；随着流程推进，`requirement_parsing`、`supplier_qualification`、`price_comparison`、`order_compliance` 依次变为实心「已加载全文」。

动作：指着中间任务树——主 Agent 三个子节点分别展开各自的工具调用与耗时。

动作：指着右侧时间线——中间件动作单独标记，例如上下文摘要事件的 token 前后对比。

讲解要点：技能是渐进式加载的，主 Agent 一开始只知道技能名和描述；子 Agent 职责被刻意切窄，业务判定是纯函数，模型只负责需求解析和说明生成——因为 DeepSeek 的工具调用稳定性不如顶级模型，把不可靠的部分压到最小是工程取舍。

## 02:00–03:00 演示异常路径

动作：切到数据台，打开「让供应商 B 资质过期」，说明当前报价表；回到看板重新提交同样的需求，进入执行页后停留在时间线，指出淘汰事件与比价结论中的改选理由。

讲解要点：注意系统没有直接选最便宜的供应商——最低价的那家资质临期，系统改选次优并把原因写进结论。这个理由不是模板，是策略引擎按规则生成的。

## 03:00–04:10 人工审批

动作：提交 `采购 3000 箱 A4 纸`，页面出现橙色审批卡片，朗读卡片上的命中规则原文。点「驳回」，填入理由「价格不合理」，观察任务回退到比价阶段重新执行，任务树出现第二轮比价。随后再触发一次并点「批准」，订单出现在数据台的订单列表中。

讲解要点：审批是持久化中断，不是进程阻塞——任务挂起期间服务重启，任务仍然在等待审批，批准后从断点继续。审批通过前订单不会写入，避免先下单后审批。

## 04:10–05:00 指标

动作：切到评测页，点「运行评测」，展示指标卡片与失败用例列表（当前 0 条）。

讲解要点：30 条固定用例、内置规则解析器、每条独立数据库，所以结果可复现。成功率与人工介入率是这条用例集上的实测值，上下文压缩率来自一个 12 段工具返回的长对话基准。需要说明的是：这些数字来自离线确定性模式，验证的是编排与治理逻辑；真实模型下的端到端指标需要配置 API key 后单独跑一遍，两者不能混着讲。

**演示前注意：** 未配置 `DEEPSEEK_API_KEY` 时页面顶部会显示橙色"离线演示模式"横幅，需求解析走内置正则解析器。因此提交需求时请写清数量与成本中心，例如 `采购 3000 箱 A4 纸，成本中心 CC-1001`——解析器不会猜。

## 可能被追问的问题

**为什么不用框架自带的 planning 当状态源？**

因为状态需要跨进程存活、需要在人工审批处挂起数小时、需要被页面直接查询与渲染。框架的规划是会话内的推理草稿，承担不了这三点。子 Agent 内部仍然可以自由使用它做局部规划。

**为什么业务判定不用 LLM？**

可测、可复现、可解释。资质过期就是日期比较，比价就是成本公式，让模型来做只会引入不必要的不确定性。模型用在真正需要理解语义的地方——把「下周一到货」变成日期。

**如果模型输出不是合法 JSON 怎么办？**

结构化输出会做 JSON 校验，失败按可重试错误处理并带上修正动作重试；超过次数上限则任务进入失败状态并保留完整错误上下文，而不是让流程带病继续。

**框架已经自带 skills / memory / permissions，你们做了什么？**

框架能力直接用，不重复造轮子；自研的是它没有的部分：任务状态机、向数据库落库的事件流、业务规则判定、mock ERP 与故障注入、Web 可视化与评测。技能那一层保留了薄封装，因为页面需要展示「已加载全文 / 仅描述」的可观测状态，测试也需要脱离框架内部实现独立运行。

**这套东西怎么变成生产系统？**

主要差距不在 Agent，而在三件事：真实的供应商与价格数据源、企业 SSO 与审批权限矩阵、容器级隔离与审计日志。`docs/sandbox-security.md` 里逐条写了演进方案与代价。
