# 安全设计：双层沙箱与审批拦截

本文件说明系统如何约束 Agent 的行为边界，以及在生产环境中应如何升级。

## 双层结构

| 层 | 位置 | 职责 | 实现 |
| --- | --- | --- | --- |
| 层一 · 策略校验 | Agent 工具调用前 | 判断「能不能做」：路径白名单、命令禁写、金额阈值、是否转人工 | `sandbox/policy.py`、`middleware/policy_guard.py` |
| 层二 · 执行隔离 | 实际执行时 | 保证「就算放行也做不出格」：受限子进程、环境变量白名单、超时、输出上限 | `sandbox/executor.py` |
| 路径层 | 所有文件读写 | 归一化 + 挂载点校验，防路径穿越 | `vfs.py` |

两层职责不同、可独立测试：层一决定放行与否，层二保证放行后的行为仍在边界内。

## 路径逃逸防护

`VirtualFileSystem.resolve` 拒绝四类输入：

| 攻击向量 | 示例 | 拒绝原因 |
| --- | --- | --- |
| 相对路径穿越 | `../../etc/passwd` | 路径段含 `..` |
| 嵌套穿越 | `a/../../x` | 同上 |
| 绝对路径 | `C:\Windows\system32` | 禁止绝对路径 |
| 写只读挂载点 | `readonly/data.txt` | 只读目录不允许写入 |

解析结果还必须落在工作区或只读挂载点之内（`is_relative_to` 二次校验），因此即使路径段通过了前置检查，越界结果仍会被拒绝。`.` 被显式映射为工作区根，避免误伤正常调用。

## 命令禁写

`DANGEROUS_COMMANDS` 采用**完全拒绝**策略，不做部分放行，包含 `rm`、`rmdir`、`del`、`erase`、`format`、`mkfs`、`curl`、`wget`、`nc`、`powershell`、`pwsh`、`cmd`、`shutdown`、`reg`、`regedit`、`sc`、`netsh`、`schtasks`。

判定方式：取 `argv[0]` 的 basename、去掉 `.exe`、转小写后与清单比对，命中即拒绝，**不启动进程**。代价是某些正当用途（例如用 `curl` 拉取公开数据）也会被拦，这是有意的取舍：把安全边界放在执行前，而不是执行后再判断。

## 执行隔离

通过校验的命令在受限子进程中执行：

- 工作目录固定在虚拟文件系统解析后的路径
- 环境变量只保留白名单（`PATH`、`SYSTEMROOT`、`PATHEXT`、`TEMP`、`TMP`、`COMSPEC`）。Windows 下不放行 `SYSTEMROOT`/`PATHEXT` 解释器无法启动，这是平台约束而非放松要求
- 执行超时默认 10 秒，超时直接终止并返回失败
- 输出上限默认 64 KB，超出部分截断并标记 `...[truncated]`
- `shell=False`，不接受 shell 元字符拼接

## 审批拦截

七条规则独立判定，命中任意一条即挂起任务等待人工审批（`sandbox/policy.py` 的 `check_lines`）：

1. 订单合计金额超过配置阈值（默认 ¥50,000，**按整单合计**而不是逐行）
2. 所选供应商资质处于临期状态
3. 推荐结果并非最低报价且差额比例超过 10%
4. 可用报价不足 `min_quote_count`（无法完成比价）
5. 交期无法满足期望到货日期
6. 采购量低于所选供应商的起订量
7. 到货批次剩余效期低于物料要求

拦截发生后，任务进入持久化的 `AWAITING_APPROVAL` 状态：状态落库、页面渲染审批卡片、进程重启后仍可批准或驳回。**审批通过前不写入订单表**，避免先下单后审批。

拦截会留下两类可查记录：

- `policy_denied`（`middleware/policy_guard.py`，在订单草稿阶段由协调器调用）：包含工具名、命中规则原文与原因；
- `approval_decided`（状态机在恢复执行时写，**唯一来源**）：包含决策、操作人、理由与来源（`web` / `api`）。

## 已知限制与生产化演进

| 限制 | 影响 | 生产化方案 |
| --- | --- | --- |
| 进程级隔离，非容器 | 无法防御内核级逃逸与提权 | 迁移到容器或微 VM，每个任务一个隔离实例，只读挂载技能与数据源 |
| 环境变量白名单仍含 `PATH` | 子进程可调用 PATH 中未被列入禁写清单的程序 | 改用固定解释器绝对路径 + 最小 PATH，或完全禁用 shell 工具 |
| 命令禁写是黑名单 | 新增工具需要同步维护清单 | 改为能力白名单：只允许显式注册的少数命令 |
| 审批人身份来自请求体 | 无法抵御伪造 | 接入企业 SSO，审批人与权限矩阵由身份系统提供 |
| 单机 SQLite | 不支持并发写入与多副本 | 迁移到 PostgreSQL，审批与订单走事务 |
| 无审计导出 | 不满足合规留痕要求 | 事件流导出为不可变审计日志，接入企业日志平台 |

这些限制在 v1 中被显式记录而非隐藏：知道边界在哪，比声称没有边界更可信。
